# Immutable OCPA building lineage

`python tools/build_building_lineage.py` recomputes relationships against all 3,916 **active** parcel features. It preserves every original building field, all 3,216 local building aliases and existing registry entity IDs. It does not publish the separate ten-parcel exclusion policy, edit the snapshot pointer, promote spatial links or alter scene/manual layers.

`validate(root)` returns the verified report with `records` as a list indexed by `id` by the caller. Exported `FIELDS` lists seven additive fields: `entity_id`, `source_building_key`, `source_building_number`, `source_object_ids`, `candidate_parcel_features`, `match_confidence_basis`, and `join_state`. Existing fields must never be overwritten. A missing/stale sidecar can leave the original snapshot usable while lineage is explicitly unavailable. Source IDs remain strings; duplicate PINs retain their separate parcel-feature candidates. Overlap fractions are not probabilities.

`data/processed/building_lineage.json` is an atomic manifest pointing to an immutable SHA-256-named JSON packet under ignored `data/derived/ocpa-lineage/`. The packet has deterministic canonical bytes; publication time is not substituted for source dates. The separate manifest receipt detects manual manifest edits. Changed packets or incomplete publication fail closed; prior manifests/receipts are backed up before replacement, and prior immutable packets remain. Replaying identical evidence reuses the existing packet without rewriting it.

The packet binds the active snapshot and exact parcel/building/raw-source/tool hashes. It also fingerprints actual base-building points, topology, world transforms and source membership, plus the registry's identity mapping. Unrelated camera metadata or registry height updates do not change these semantic fingerprints. Geometry fingerprint calculation is cached only against the full on-disk source-file SHA; a changed file is reopened anonymously before calculation. No editor layer is reloaded or saved.

Every modeled source object must exist in raw OCPA subareas and agree on original PID/building number; duplicated assignments or registry membership changes require explicit reconciliation. Entity IDs reuse the existing source-membership hash and do not guarantee permanent physical identity after splits, merges or republication. The current extract has 13,999 raw subareas and 13,926 modeled memberships; 73 unrepresented records across 46 source groups remain in `membership.orphan_queue`, distinguishing partially represented groups from wholly absent ones. This is not a confirmed missing-building census and causes no automatic attachment or reconstruction.

Current relationship counts remain 2,976 accepted source-ID/geometry links, 202 spatial-review, three ambiguous and 35 unmatched. Three focused checks cover preservation of nonidentity fields, row-order identity stability, duplicate-PIN candidate separation, registry/raw reconciliation, immutable replay, backups, manual-output guards and path containment. Independent acceptance and full #3 property/sketch/coverage disposition remain separate requirements.

## Integrated inspection

The local API exposes `/api/v1/building_lineage` (paginated records) and `/api/v1/building_lineage_quality` (fields, counts, dependencies and orphan queue). Building responses add verified lineage without replacing existing fields; missing or stale lineage leaves the original snapshot usable and labels the lineage unavailable. The property inspector expands Building source evidence for both assigned and candidate exact parcel features. Disable Link property selection with 3D for map-only review.
